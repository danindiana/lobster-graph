# Pinning the Model Entirely to the GTX 1060 (GPU1)

**Date:** 2026-08-19
**Unix timestamp:** 1787167674
**Session folder:** `docs/sessions/1787167674_pin-model-gtx1060/`

## Objective

`paper_proc_smrtevict.py` (and this whole repo) is a transplant from another
machine — the user confirmed this session that the hardware is not what the
code's comments assume. The prior session (`2026-08-19_013917_smrtevict-resume-
model-tuning-overnight-launch.md`) already found the `MODEL_GPU_LAYERS`
comments reference an RTX 5080 + RTX 3080 host; the real box here
(`dellt3600`) is a **Quadro P4000 (8 GB) + GTX 1060 6GB (6 GB)**. This
session's goal: get the model running **entirely in VRAM on the GTX 1060
only**, with the Quadro P4000 left untouched, since the shared system Ollama
daemon (`CUDA_VISIBLE_DEVICES=0,1`) was tensor-splitting even a 3.6 GB model
across both cards over PCIe (no NVLink between these two cards — every
cross-device layer boundary pays a transfer cost).

## What was found

- The overnight batch launched in the prior session had actually **already
  finished** (604/604 papers) by the time this session started — the
  `kill -TERM` sent to PID 81524 landed right as it was exiting on its own.
  No interrupted work, no resume risk.
- The system Ollama daemon (`ollama.service`, `CUDA_VISIBLE_DEVICES=0,1` via
  `/etc/systemd/system/ollama.service.d/override.conf`) was left untouched —
  approach chosen was an **additive isolated backend** (matching the existing
  `docs/sessions/2026-06-04T14-03-40_gpu_telemetry/start_isolated_backends.sh`
  precedent in this repo), not a system-wide reconfig.

### The real gotcha: Ollama 0.32.14 has two independent GPU backends

Setting `CUDA_VISIBLE_DEVICES=1` on a fresh `ollama serve` instance was
**not sufficient** — the scheduler still picked the Quadro P4000. Server
startup logs showed why:

```
inference compute id=0 filter_id=1 library=CUDA  name=CUDA0   description="NVIDIA GeForce GTX 1060 6GB" pci_id=0000:04:00.0
selecting single GPU for llama-server model main_gpu=0 id=1 filter_id=1 library=Vulkan name=Vulkan1 description="Quadro P4000"
```

Ollama 0.32+ discovers compute devices via **both CUDA and Vulkan**
independently. `CUDA_VISIBLE_DEVICES` only filters the CUDA backend — the
Vulkan backend enumerates every physical GPU regardless, and the scheduler
was free to (and did) pick the Vulkan-visible P4000 instead of the
CUDA-visible 1060. `nvidia-smi` confirmed it: GPU0 (P4000) picked up
~3 GB, GPU1 (1060) stayed at 3 MiB.

**Fix:** also set `OLLAMA_VULKAN=0` on the isolated instance, which removes
the P4000 from discovery entirely and leaves only `CUDA0` (the 1060) as a
selectable device.

## What was built

`start_gpu1_backend.sh` (this folder) — starts a second, independent Ollama
daemon:
- `OLLAMA_HOST=127.0.0.1:11435` (separate port; the shared system daemon on
  11434 is untouched)
- `CUDA_VISIBLE_DEVICES=1` + `OLLAMA_VULKAN=0` — the two settings together
  are what actually confine it to the GTX 1060
- `OLLAMA_MODELS=/home/ollama_models` — this box's real models dir (the
  original `start_isolated_backends.sh` template defaults to
  `/usr/share/ollama/.ollama/models`, which is wrong here)

Detached via `nohup ... &`, PID tracked in `/tmp/ollama_gpu1.pid`, log at
`/tmp/ollama_gpu1.log`.

## Verification

1. `curl 127.0.0.1:11435/api/generate` (single prompt) → `ollama ps` reported
   `100% GPU`; `nvidia-smi` showed GPU0 at 3 MiB, GPU1 at ~2975 MiB.
2. Server log confirmed full residency:
   ```
   llama_prepare_model_devices: using device CUDA0 (NVIDIA GeForce GTX 1060 6GB) (0000:04:00.0) - 5997 MiB free
   load_tensors: offloaded 36/36 layers to GPU
   ```
3. Full-pipeline validation: `--paper 1301.3781.pdf --reprocess all` (all
   five sections: summary, logic, cpp, 6 diagrams, extras — the diagrams
   section is the heaviest VRAM/context consumer per the prior session's
   notes). Polled `nvidia-smi` every 10s through the run — GPU0 stayed at
   3 MiB / 0% the entire time; GPU1 held steady at ~2975 MiB with generation
   throughput ~31-32 tok/s.

## Progress-check anomalies, explained

A progress check shortly after launch turned up two things that looked odd
at first but are both benign, confirmed with the user:

- **PDF count kept climbing** (400 → 1598 → 1609 within a 5s window). Cause:
  a human-operated `rsync` (PID 157054/157055, started 14:29 in a separate
  terminal, independent of this session) is actively transferring more PDFs
  into `aug_8_2026` in real time. Not something this session started or
  needs to manage — the batch just works through whatever's on disk as it
  grows, so the true total/ETA is a moving target until that transfer
  finishes.
- **`_processed/` already contained ~2149 near-empty directories** before
  this run's first paper even completed, all stamped the same instant
  (14:29:54) — the script's startup batch-scan pre-creates a placeholder dir
  per PDF it discovers, so this is not evidence of prior completions on its
  own. Confirmed with the user: these are leftovers from a **separate
  `paper_proc` nohup run against this folder the night before** this
  session — genuine prior work, not a bug or stale transplant artifact.
  Real completion is tracked by a populated `metadata.json` inside each
  dir, not by the dir's mere existence.
